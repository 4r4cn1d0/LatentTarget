# Work through to a bounded RunPod diagnostic

The user authorized continuing local preparation through RunPod readiness.
No pod is created by this stage. This is not permission to bypass the original
confirmation checkpoint or reinterpret failed historical gates.

## Fixed scope before new outcomes

1. Build one grounded bank, with three development and three evaluation scenario
   families. State the facts that support Option A; also give Option B a modest
   convenience advantage. Target assignment never changes those facts.
2. Use the development families for histories and fitting lexical adversaries.
   Fit positive versus reversed similarity separately for familiar, near and
   composite candidates on development bundles. Freeze signs before evaluating
   the separate scenario families. Do not edit the bank after audit outcomes.
3. Audit all five existing shallow similarities, plus annotated feature reward
   and belief references. Keep every policy, sign, seed and failure. This is an
   exploratory diagnostic bank, not a validated confirmation set.
4. Show the additive simulator's observational equivalence explicitly:
   p(A | x, history) = 0.38 + 0.34 sum_t belief[t] x[t] = dot(x, q),
   where q[t] = 0.38 + 0.34 belief[t] and sum_t x[t] = 1.
   Test predictions and choices for random posteriors and message mixtures.
   Generic reward learning is not thereby ruled out. No more elaborate game
   or activation experiment is implemented to conceal that limit.
5. Obtain two blind machine judgments of the complete grounded messages,
   through the existing isolated Codex measurement interface if available.
   The judge receives the scenario, options and message, not target types,
   outcomes, policy results, registered vectors or split labels. Preserve raw
   outputs. Machine review is not independent human validation. Codex calls
   consume account usage; they are not described as free computation.
6. Prepare a diagnostic pilot containing exactly three complete bundles and
   60 selected choice requests (five branches, four cells each). Forecasts
   remain in the offline ledger but are excluded from this first constrained
   digit pilot. Keep all three bundle transcripts. No inferential claim at N=3.
7. Build a portable, explicit allowlist artifact package with hashes and a
   runner that refuses mismatched files, duplicate responses, altered prompts,
   unknown models, too many requests and accidental activation capture.
   Mock dry runs must exercise recording, interruption and resume behavior.
8. Verify a current official open weight checkpoint, pin its revision, check
   public RunPod prices, and prepare a capped single GPU run plan. GPU loading,
   tokenizer compatibility, runtime and real response validity remain untested
   until the pod smoke check. No automatic confirmation run follows.

## Fixed audit coordinates

Development seed: 202609086. Evaluation seed: 202609087. Each audit split has
36 independently generated, balanced bundles. Candidate order and ordered
target pair cover all 36 combinations. This is an engineering and confound
screen, not another 5,000 study power search.

Lexical methods: original Jaccard, content Jaccard, shallow stem Jaccard,
character trigram and length similarity. Each sign is selected by its mean
development contrast, ties selecting positive. No evaluation labels enter
selection. The no history control uses no history; the random response
control uses fair coin outcomes. Mathematical references retain declared
privileged frame annotations, and are not models of language understanding.

Machine judges: gpt-5.6-sol and gpt-5.6-luna using separate isolated calls and
separate artifact directories, fixed batch size 18. They share a model family
and are not statistically independent witnesses. Only a single pass per
message per judge is planned; do not rerun valid unfavorable judgments.

## Readiness is explicit

Engineering readiness means the package and recording code work locally.
Diagnostic pilot readiness requires exact prompts, limits, unresolved
scientific limitations and a model/runtime plan to be visible to the user.
Confirmation readiness additionally requires scientific validation and a
separate approval. These are three different statuses.
